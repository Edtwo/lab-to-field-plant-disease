# Internal pre-submission review

We reviewed the draft (`paper/main.pdf`, 7 pages) from three reviewer perspectives. Scores use 1 = strong reject … 5 = strong accept.
"Fixed" marks issues addressed before submission, with the evidence. "Open" marks what remains.

---

## Reviewer 1: CV methods expert. Score: **3 / 5 (weak accept for a workshop)**

**Strengths.** Clean controlled design. Pre-registered falsifiable claims, two of which are reported as falsified. Paired bootstrap tests instead of bolding means. The frozen-beats-fine-tuned DINOv2 result is useful and now has a robustness check.

**Concerns.**
1. *Hyperparameters were never tuned, so the FT vs. LP result could be an artifact.* → **Fixed.** Ran an LR sensitivity check (1e-5 / 5e-5 / 2e-4, 3 seeds each, `results/runs/dinov2s_ft_pv_pre_lr*`). Fine-tuning stays below the probe at every LR (29.9–39.7 vs 46.2). See Sec. 6 / Tab. "sens". Also stated clearly as post-hoc and not used for selection.
2. *No domain-adaptation baselines (DANN, CORAL, test-time adaptation, background augmentation).* → **Open.** Out of scope for the budget and deadline. Listed as future work. Idea 2 (background-paste augmentation) was not run.
3. *Only small backbones; no DINOv2-B/L, no stronger CLIP (e.g. ViT-L/14).* → **Open.** This is deliberate (edge focus) but limits the "foundation model" conclusion to ViT-S. Should be stated in Limitations (done: "Compute and tuning").
4. *11 paired comparisons with no multiple-comparison correction.* → **Partly fixed.** Disclosed in the Tab. 3 caption. 10 of the 11 CIs exclude 0, and the most marginal significant one (LP: PV→all vs. field-only, CI [−8.8, −2.0]) still has its upper bound well away from 0. A Holm correction was not computed. **Open.**
5. *The LP regimes use PV-head initialization for "PV→" but a fresh head for "only". The negative-transfer finding for LP may be a head-initialization effect rather than a "lab data" effect.* → **Fixed (by analysis, no run needed).** For the frozen probe the backbone is identical in both arms, so the difference *is* the head initialization by construction. The abstract, intro, results, ablations and conclusion were reworded to say exactly that, instead of "lab pretraining hurts DINOv2". The remaining open question is whether a longer schedule would close the gap.

## Reviewer 2: Agriculture domain expert. Score: **3 / 5**

**Strengths.** Asks the question practitioners care about ("will lab-trained models work on my photos, and how many field photos do I need?"). Gives honest negative results. The broader-impact section is sensible (decision support, not diagnosis).

**Concerns.**
1. *"Field" = PlantDoc web images, not images from a real farm, season, or device.* → **Fixed in text.** Limitations states this explicitly. The data still cannot fix it. **Open** as a data limitation.
2. *Many PlantDoc classes are "healthy leaf of crop X", so part of the task is crop ID, not disease diagnosis.* → **Fixed.** Added an error decomposition (Tab. "errors"): lab CNNs get the crop wrong ~45% of the time. The DINOv2 advantage is mostly crop recognition. Healthy-vs-diseased accuracy is reported against a majority baseline (61.9%).
3. *Per-disease breakdown missing (some diseases visually distinct, e.g. rust, vs. subtle).* → **Open.** Per-class logits are saved, but with 4–12 test images per class, per-class numbers would be noise. A per-class table could go in a supplement.
4. *Label quality of PlantDoc not verified by pathologists.* → **Open.** Acknowledged in Limitations. Cannot fix.
5. *Crop coverage (13 temperate/horticultural crops) excludes staples.* → Stated in Limitations.

## Reviewer 3: Reproducibility chair. Score: **4 / 5**

**Strengths.** Every number in the paper comes from LaTeX macros generated by `scripts/summarize.py` out of per-run `metrics.json`/logits. Configs, seeds, pinned `requirements.txt`, a resumable `run_matrix.py`, verified citations with URLs, license table, and the near-duplicate audit.

**Concerns.**
1. *Not bit-exact (cudnn.benchmark, bf16).* → Disclosed in README. **Open** (acceptable).
2. *Windows-specific path workarounds (short venv/data paths).* → Documented in README.
3. *Public code link.* → **Fixed.** The repository is public and linked in the abstract.
4. *Edge latency measured on a desktop CPU (Ryzen 7 9800X3D), not on edge hardware.* → Disclosed. C4 is interpreted with that caveat. **Open:** a Raspberry Pi / phone measurement would make the "edge-aware" title fully earned.
5. *The smoke test (≈6 min) is not counted in the GPU-hours.* → Stated in the paper.
6. *Post-hoc analyses (LR sensitivity, error decomposition) are mixed with pre-registered ones.* → **Fixed.** Both are labeled post-hoc/exploratory in the text, and the claim check in `results/summary.md` uses only the thresholds from `notes/plan.md`.

---

## Average: 3.3 / 5. Plausible workshop accept as a benchmark/analysis paper; not as a methods paper.
